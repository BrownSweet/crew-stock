# 公司、行业与公众人物长期研究档案：关键设计模板

> 文档状态：模板草案  
> 当前版本：`0.7`  
> 文档用途：作为后续设计讨论和实现的唯一修改基线  
> 更新原则：后续对工作模式、目录、数据规则和定时任务的讨论，均回写到本文档

## 1. 设计目标

建立一套可长期维护、可追溯、可复盘的公司、行业与相关公众人物研究档案系统。

系统用于研究和决策辅助，具体包括：

- 建立公司的长期研究档案；
- 自动整理财报、监管文件和电话会信息；
- 对比管理层承诺与实际结果；
- 跟踪行业数据和竞争对手；
- 建立公司上下游产业、供应链关系和冲击传导图；
- 跟踪对公司和行业叙事具有影响力的公众人物及其观点；
- 标注公司指引和市场预期的变化；
- 区分事实、推测与市场情绪；
- 记录投资逻辑在什么时候、因为什么发生改变；
- 帮助用户复盘自己的决策过程。

## 2. 非目标与安全边界

本系统不是“保证赚钱的荐股工具”，不承诺收益，不代替用户做最终投资决策。

默认安全边界：

- 自动金融数据优先使用 Longbridge 的只读能力；允许用户主动上传与研究相关的公开内容和个人批注；
- 禁止定时任务下单、撤单、改单或自动调仓；
- 禁止将模型生成的判断冒充为已确认事实；
- 重要结论必须能回溯到原始来源；
- 投资逻辑的实质性修改需要人工确认；
- 用户决策日志只能由用户确认，自动任务只能提出待确认建议。

## 3. 核心工作模式

### 3.1 推荐模式

采用：

**本地研究仓库 + Longbridge 数据能力 + Codex 独立定时任务 + 人工决策门**

其中：

- 本地目录是长期记忆和唯一事实基线；
- Longbridge MCP 负责交互研究、单对象试点和能力探测；
- Longbridge CLI 在完成独立授权与连通性验证后，负责批量、可复现采集和完整正文落盘；
- `longbridge:longbridge` skill 负责把研究意图路由到合适的 Longbridge 只读工具，不把 skill 本身视为数据来源；
- Codex 负责协调采集、变化识别、资料整理、档案更新和研究报告生成；
- 用户负责确认投资逻辑变更和最终决策。

### 3.2 不采用的模式

- 不把单个长聊天作为长期数据库；
- 不让每次定时任务从零重新生成公司介绍；
- 不只保留 Codex 总结而丢弃原始数据；
- 不在无来源、无时间截面的情况下覆盖旧判断。

## 4. 系统分层

系统严格区分三类职责：

1. **事实与内容采集**：由 Longbridge 只读能力、用户上传和其他已授权来源提供；
2. **确定性处理**：由普通代码完成 ID 分配、哈希、去重、字段校验、期间对齐、差异计算和可复现数值运算；
3. **语义研究**：由 LLM 完成文本抽取、事实/推测/情绪分类、跨期解释、观点归因、冲突发现和待确认判断建议。

LLM 不负责伪造缺失数据、替代精确计算、静默修正原始证据或代替用户确认投资逻辑。

```text
Longbridge / 用户上传 / 已授权公开来源
        ↓
本地不可变快照
        ↓
本次与上次数据差异
        ↓
事实 / 推测 / 市场情绪分类
        ↓
公司 / 证券 / 行业长期研究档案
        ↓
重要变化提醒与人工审阅
```

### 4.1 原始证据层

保存 Longbridge MCP/CLI 输出的 JSON、监管文件 Markdown、新闻正文、用户上传文件、公开链接快照和其他原始结果。

规则：

- 原始数据只追加，不覆盖；
- 每次采集保留时间、命令、数据截止日期和内容哈希；
- 每次采集同时保存数据提供方、传输方式、工具名称、请求参数、返回状态和失败原因；
- 相同文件或数据快照需要去重；
- 当命令失败时，记录失败，不伪造空数据或沿用旧数据冒充新结果。

### 4.2 变化识别层

对比本次与上次快照，只提取新增或实质性变化：

- 新财报或新监管文件；
- 管理层新承诺或原有承诺的口径变化；
- 收入、利润、现金流和关键运营指标的变化；
- 公司指引与市场一致预期变化；
- 行业数据或竞争对手的实质性变化；
- 可能影响投资逻辑的新证据。

### 4.3 研究判断层

更新公司画像、管理层承诺、预期变化、竞争格局和投资逻辑。

所有判断必须：

- 标明类型；
- 指向原始证据；
- 包含判断生效的时间截面；
- 区分“新增判断”与“修改旧判断”；
- 保留修改理由，不静默覆盖历史结论。

### 4.4 个人决策层

记录用户当时的信息、假设、决策和后续复盘。

Codex 可以：

- 整理当时已知信息；
- 指出决策中未验证的假设；
- 提醒原有逻辑与新证据之间的冲突；
- 生成待用户确认的复盘问题。

Codex 不能：

- 自动代替用户填写最终买卖理由；
- 在没有确认的情况下宣布投资逻辑已改变；
- 将事后获得的信息写成当时已知信息。

## 5. 研究对象模型与目录模板

### 5.1 基础研究对象

系统区分四类基础对象：

| 层级 | 研究对象 | 主要内容 |
| --- | --- | --- |
| 公司主体 | 实际经营、合并报表和信息披露主体 | 财报、业务、管理层、承诺、公司指引和投资逻辑 |
| 可交易证券 | 公司发行的具体股票或其他可交易证券 | 代码、市场、股权类别、投票权、价格、估值、流通量和公司行动 |
| 行业 | 跨公司的研究集合 | 产业链、供需、周期、产能、技术路线、关键指标和参与者 |
| 公众人物 | 对公司、行业、政策或市场叙事具有可观察影响力的公开人物 | 公开身份、历史关系、观点、预测、解读、传播范围和后续验证 |

基础对象的关系：

```text
公众人物 ──观点/影响──→ 公司主体 / 行业 / 证券
                               ↑
行业 ←──多对多──→ 公司主体
                               ↓
                      零个或多个可交易证券
```

### 5.2 统一模板原则

公司、证券、行业和公众人物共用一套底层研究协议，包括：

- 证据来源和原始数据引用；
- 业务截止时间和本地采集时间；
- 事实、推测和市场情绪分类；
- 研究逻辑、反方证据和可证伪条件；
- 历史版本和变更原因。

不同研究对象使用不同的上层模板：

- 公司模板：管理层、财报、业务结构、承诺和指引；
- 证券模板：交易代码、市场、股权类别、投票权、估值和公司行动；
- 行业模板：产业链、供需、周期、技术路线、指标和参与者。
- 公众人物模板：公开身份、时间化关系、观点、传播影响、历史验证和争议性说明。

### 5.3 公司主体与多证券规则

公司目录使用稳定的 `company_id`，不使用可能变更的证券代码作为公司主键。

公司主体可以拥有零个或多个可交易证券。未上市公司仍然可以建立完整公司档案，不强制创建 `sec-*` 对象。

同一公司发行的多个可交易证券归属同一公司档案。例如：

```text
companies/
└── cmp-000001/
    ├── cmp-000001.yaml
    ├── documents/
    │   ├── doc-000001/
    │   └── doc-000002/
    └── securities/
        ├── sec-000001/
        │   └── sec-000001.yaml
        └── sec-000002/
            └── sec-000002.yaml
```

其中公司名 `Alphabet Inc.` 和证券代码 `GOOGL.US`、`GOOG.US` 保存在对应 YAML 元数据中，不用作永久目录名。

存储边界：

- 合并财报、监管文件、电话会、管理层承诺和公司业务分析存放在公司层；
- 证券代码、上市市场、股权类别、投票权、价格、估值和流通信息存放在证券层；
- 公司经营逻辑存放在公司层；
- 选择具体股权类别或交易标的的理由存放在证券层。

### 5.4 行业与公司引用规则

行业目录只保存行业自身的研究内容和公司引用，不在行业目录下复制完整公司档案。

原因：

- 一家公司可以同时属于多个行业或研究主题；
- 复制公司档案会导致多份数据和研究逻辑不一致；
- 公司业务边界变化时，引用关系比目录搬迁更稳定。

行业成员使用 `company_id` 引用，并可记录公司在该行业中的角色：

```yaml
industry_id: ind-000001
display_name: memory-semiconductors
members:
  - company_id: cmp-000002
    display_name: Micron
    role: DRAM/NAND
  - company_id: cmp-000003
    display_name: SK Hynix
    role: DRAM/HBM/NAND
  - company_id: cmp-000004
    display_name: SanDisk
    role: NAND/storage
```

### 5.6 ID 文件夹规则

凡是可以被独立引用、更新、审计或归档的最下层对象，必须建立为独立 ID 文件夹。

文件夹内的文件使用与文件夹相同的 ID 命名，通过扩展名区分元数据和内容载荷。例如：

```text
evd-000001/
├── evd-000001.yaml
└── evd-000001.json

doc-000001/
├── doc-000001.yaml
└── doc-000001.md
```

规则：

- 集合型目录使用固定语义名称，如 `companies/`、`industries/`、`evidence/`；
- 集合型目录下的最小对象必须是 ID 文件夹；
- 对象的主元数据文件为 `<id>.yaml`；
- 内容载荷使用同一 ID，例如 `<id>.md`、`<id>.json` 或 `<id>.html`；
- 一个 ID 只表示一个研究对象，不得跨对象复用；
- ID 创建后永久不变，名称、证券代码或行业归类变更时不修改 ID；
- 删除的 ID 不得重新分配，应保留停用或归档记录；
- 编号格式和类型前缀以 [ID 编号规则表](methodology/id-rules.md) 为准。

### 5.7 上下游产业与供应链图

供应链采用“有向加权影响图”，用于表达上游供应变化如何沿关系传导到公司、下游企业和终端需求。

界面可以表现为类似神经网络或数据血缘图，但底层是可解释的供应链因果影响模型，不将其描述成已训练的神经网络。

#### 5.7.1 节点

节点直接引用已有永久 ID，不再复制对象：

- 公司主体 `cmp-*`；
- 行业或产业环节 `ind-*`；
- 需要对具体可交易证券分析时使用 `sec-*`；
- 关键事件和冲击来源可引用 `evt-*`。

#### 5.7.2 关系边

每条供应链边是全局唯一的 `rel-*` 对象，只保存一份，公司图和行业图通过 ID 引用它。

最小元数据：

```yaml
id: rel-000001
type: relation
relation_type: supply
upstream_id: cmp-000002
downstream_id: cmp-000001
input_category: advanced-chip-foundry
direction: upstream_to_downstream
dependency_weight: 0.82
confidence: 0.68
weight_status: model_proposed
model_version: <model-version>
as_of: 2026-08-03
evidence_ids:
  - evd-000001
last_reviewed_at: 2026-08-03T12:00:00+08:00
```

关系是有方向的，同两家公司在不同方向上可以有不同权重。例如，供应商停产对客户的影响，不等于客户砍单对供应商的影响。

#### 5.7.3 权重生成

`dependency_weight` 范围为 `0.00–1.00`，由模型按统一评分表生成初始建议：

| 因素 | 比例 | 判断内容 |
| --- | ---: | --- |
| 输入关键性 | 25% | 缺失该输入是否会直接阻断生产或交付 |
| 可替代性 | 20% | 是否有可快速切换、已认证的替代供应商 |
| 供应集中度 | 20% | 供应是否集中在少数公司、工厂或地区 |
| 交期与库存缓冲 | 15% | 长交期、库存天数和安全库存是否放大或吸收冲击 |
| 经济暴露 | 10% | 采购、收入、产量或成本对该关系的暴露程度 |
| 地理与监管风险 | 10% | 地缘、物流、贸易和监管是否会放大关系风险 |

每项因素先评为 `0.00–1.00`，再按上表加权合成。

权重不属于客观事实，必须同时保存：

- 各评分项的证据和理由；
- 综合置信度 `confidence`；
- 使用的模型版本；
- 生成时间和数据截止日期；
- `model_proposed`、`human_confirmed` 或 `rejected` 状态；
- 人工覆盖前后的历史权重和理由。

#### 5.7.4 冲击传导

一次模拟保存为 `sim-*` 情景对象，至少包含：

- 冲击源节点；
- 冲击方向和幅度；
- 时间范围；
- 参与计算的关系版本；
- 各路径的传导结果；
- 缓冲、替代供应和库存假设；
- 结果的置信度和局限。

对一条边的基础传导可表示为：

```text
有效传导 = 上游冲击 × 依赖权重 × 置信度 × 时间范围因子
```

多条路径汇入同一节点时，采用有上限的合并方式，避免简单相加导致影响超过 100%。需要显式识别循环关系，使用阻尼系数避免无限反馈。

传导结果是情景估算，不是股价涨跌预测。

#### 5.7.5 联动交互

供应链图至少支持：

- 点击任意上游、公司或下游节点作为冲击源；
- 调整冲击方向、幅度和时间范围；
- 高亮所有受影响路径；
- 根据传导结果动态更新节点影响强度；
- 展示每条边的权重、置信度、证据和最近审核时间；
- 区分模型建议权重和人工已确认权重；
- 从公司图下钻到证据和对应研究档案；
- 切换“直接一级”、“多级传导”和“指定行业”视图。

### 5.8 公众人物、观点与用户上传

系统允许为对公司、行业、政策或市场叙事具有明显影响力的公众人物建立独立档案。

公众人物不必是公司员工、管理层或股东。人物与公司的任职、投资、顾问、合作、竞争、评论或叙事影响关系，均作为带时间范围的 `rel-*` 关系存储，不写成人物的永久静态属性。

#### 5.8.1 公众人物对象

公众人物使用 `per-*` ID，至少包含：

```yaml
id: per-000001
type: person
display_name: <public-name>
aliases: []
public_roles: []
jurisdictions: []
topics: []
status: active
created_at: 2026-08-03T12:00:00+08:00
```

档案只保存与公司、行业和研究主题有关的公开信息，不收集无关的私人生活、敏感个人信息或未公开数据。

#### 5.8.2 观点对象

每个可独立引用的观点、预测或解读使用 `opn-*` ID，不直接覆盖人物或公司档案。

最小元数据：

```yaml
id: opn-000001
type: opinion
person_id: per-000001
subject_ids:
  - cmp-000001
statement_type: interpretation
stance: mixed
published_at: 2026-08-03T10:30:00+08:00
source_evidence_ids:
  - evd-000001
summary: <structured-summary>
extraction_confidence: 0.86
support_status: unresolved
influence_weight: 0.64
weight_status: model_proposed
as_of: 2026-08-03
```

`statement_type` 至少区分：

- `fact_claim`：人物对可核验事实的声称；
- `interpretation`：对已知事实的解读；
- `prediction`：对未来结果的预测；
- `value_judgment`：价值判断或个人立场；
- `sentiment_signal`：主要表达乐观、悲观、支持或反对的传播信号。

`support_status` 至少区分：

- `unresolved`：暂无足够证据验证；
- `corroborated`：已被独立证据支持；
- `partially_corroborated`：仅部分得到支持；
- `contradicted`：已被更强证据否定；
- `not_verifiable`：属于无法客观验证的价值判断。

#### 5.8.3 影响力与可信性分离

`influence_weight` 表示该人物的表述在指定主题和时间范围内可能影响市场叙事或公众认知的强度，不表示其说法是正确的。

模型使用以下统一评分表生成初始影响权重：

| 因素 | 比例 | 判断内容 |
| --- | ---: | --- |
| 公开触达与传播范围 | 25% | 稳定受众、内容传播和二次放大能力 |
| 主题相关性与专业性 | 25% | 人物经历与当前研究主题的关联度 |
| 信息接近度 | 20% | 是否可能接近一手业务、技术或政策信息 |
| 历史市场反应 | 20% | 过往类似表述是否曾产生可观察的叙事或行为变化 |
| 时效性与语境完整度 | 10% | 表述是否当期、完整，是否存在截取上下文 |

以下三者不得混合：

- `influence_weight`：可能影响多大；
- `extraction_confidence`：系统是否准确理解了人物的原始表述；
- `support_status`：该表述是否被外部证据支持。

不给公众人物生成简化的“可信度人品分”。历史预测和事实声称按具体主题、时间和证据分别复盘。

#### 5.8.4 用户上传与主观批注

用户可以上传：

- 社交媒体链接或导出内容；
- 截图、图片、PDF、视频、音频或转写文本；
- 自己整理的人物观点；
- 对原始内容的个人解读和批注。

每次上传或手工提交使用 `sub-*` 对象保存。

用户上传的原始内容、用户自己的批注和系统抽取结果必须分开：

```text
sub-* 用户提交
├── att-* 原始附件
├── user_note 用户主观批注
└── extracted_objects
    ├── evd-* 可引用证据
    └── opn-* 结构化观点
```

处理流程：

1. 保存原始文件、原文链接、上传时间和内容哈希。
2. 对图片、音频和视频生成 OCR 或转写结果，保留提取置信度。
3. 识别公众人物；身份不唯一时标记待确认，不自动归档。
4. 区分原文中的事实声称、解读、预测、价值判断和情绪信号。
5. 将用户批注作为 `user_annotation` 保留，不冒充人物原话。
6. 检查相同链接、内容哈希和重复观点。
7. 将观点关联到一个或多个公司、行业、证券或事件 ID。

只有用户自行输入、没有可定位原始来源的内容，必须标记为 `user_provided_unverified`，不能转换成已验证的人物观点。

#### 5.8.5 观点驱动归档

用户提交和外部观点可以作为公司或行业建档的入口。系统先保存观点原文，再识别和关联研究对象，不要求用户预先选定公司目录或行业目录。

处理链路：

```text
sub-* 原始提交
    ↓
作者、时间、来源和观点类型抽取
    ↓
公司 / 证券 / 行业 / 事件 / 关系候选识别
    ↓
优先匹配已有永久 ID
    ↓
未匹配对象进入待建档候选
    ↓
用户确认后由确定性程序分配 ID
    ↓
opn-* 与一个或多个对象建立引用
```

归档规则：

- 一份原始内容只保存一次，不得复制到多个公司或行业目录；
- 一个 `opn-*` 可以通过 `subject_ids` 同时关联多个 `cmp-*`、`sec-*`、`ind-*`、`evt-*` 或 `rel-*`；
- LLM 负责实体识别、别名解析、观点分类和候选关联，不负责分配永久 ID；
- 优先查找中央登记表中的已有对象，防止公司重名、多证券混淆和行业重复；
- 找不到匹配对象时，只在 `sub-*` 中生成 `entity_candidates`，状态必须是 `pending_confirmation`；
- 用户确认新对象后，确定性 ID 分配器创建正式对象，再回填观点引用；
- 无法唯一识别的公司、证券、人物或行业保持 `unresolved`，不得强行归档；
- 观点可以触发 Longbridge 只读核验、公司或行业建档建议、供应链关系建议和研究待办；
- 观点不得直接修改公司事实、已确认供应链权重、管理层承诺状态或投资逻辑。

候选对象建议结构：

```yaml
entity_candidates:
  - mention: SK Hynix
    suggested_type: company
    matched_id: null
    match_status: not_found
    confidence: 0.96
    suggested_action: create_company_candidate
    status: pending_confirmation
```

#### 5.8.6 与影响图联动

公众人物作为 `per-*` 节点加入影响图，但与供应链运营边分开。

关系边至少区分：

- `supply`：供应与生产依赖；
- `demand`：需求与收入暴露；
- `affiliated_with`：任职、投资、顾问或合作关系；
- `comments_on`：对某对象或主题公开发表观点；
- `narrative_influence`：对市场叙事或公众认知的影响；
- `policy_influence`：对政策或监管讨论的影响。

影响图中需要分开计算和展示：

- 运营与供应链影响；
- 需求与收入影响；
- 市场叙事和情绪影响；
- 政策与监管影响。

不得将公众人物的言论影响权重直接套入供应链停产的传导公式，也不得因为人物影响力高就自动修改公司事实或投资逻辑。

#### 5.8.7 内容与人物安全边界

- 默认只为公开人物建档；
- 只保存与研究主题直接有关的公开信息；
- 对未验证身份、截图来源或转述内容明确标记不确定性；
- 不对人物的私人生活、医疗状况、心理状态或其他敏感特征做无证据推断；
- 不把争议性表述改写为系统自身结论；
- 引用原文时保留来源和必要上下文，研究记录优先保存结构化摘要和短引文。

## 6. 证据记录契约

每条关键记录至少包含：

```yaml
id: evd-000001
type: evidence
as_of: 2026-08-03
captured_at: 2026-08-03T08:30:00+08:00
content_classification: fact
source: longbridge
command: longbridge filing AAPL.US --format json
original_url: null
raw_path: raw/filings/example.json
source_id: example-id
content_hash: example-sha256
confidence: high
```

字段规则：

- `as_of`：数据表达的业务截止日期；
- `captured_at`：本地实际采集时间；
- `type`：对象类型，本契约中为 `evidence`；
- `content_classification`：内容分类，使用 `fact`、`inference`、`sentiment`、`opinion` 或 `user_annotation`；
- `source`：数据来源；
- `command`：可复现本次采集的只读命令；非 CLI 来源可为空；
- `original_url`：原始公开内容链接；本地上传可为空；
- `raw_path`：本地原始证据路径；
- `source_id`：原始系统的文件、新闻或数据标识；
- `content_hash`：用于去重和证明原始内容未被静默替换；
- `confidence`：对判断可靠性的评估，不表示未来收益概率。

## 7. 研究内容分类

### 7.1 事实 `fact`

能被可定位的原始来源直接支持的内容。

例如：财报数字、公司正式指引、监管文件内容、管理层原始表述。

### 7.2 推测 `inference`

基于一个或多个事实得出的分析判断。

推测必须同时记录：

- 支持它的事实；
- 中间推理过程；
- 可能的反例；
- 能证伪它的后续指标。

### 7.3 市场情绪 `sentiment`

市场参与者当前的偏好、担忧或叙事，不等同于公司事实。

情绪数据必须标明时间窗口，并与事实和研究结论分开存放。

### 7.4 外部观点 `opinion`

可定位到具体人物、机构或公开来源的事实声称、解读、预测或价值判断。

观点必须保留发表人、来源、时间、上下文、结构化摘要和证据支持状态。

### 7.5 用户批注 `user_annotation`

用户对原始内容或研究对象的主观解读、标注和待验证想法。

用户批注必须与原文、人物观点和系统推测分开存储，不得伪装成原始来源内容。

## 8. 管理层承诺跟踪

每项承诺建议记录：

- 承诺内容；
- 首次提出时间；
- 原始来源和原文位置；
- 目标时间或报告期；
- 可验证指标；
- 当前状态：待验证、部分兑现、已兑现、延期、改口径、未兑现；
- 最新证据；
- 状态变更历史；
- Codex 判断与人工确认状态。

## 9. 投资逻辑变更

`thesis.md` 至少包含：

- 当前核心逻辑；
- 支持逻辑的已知事实；
- 仍未验证的假设；
- 关键观察指标；
- 可以证伪逻辑的条件；
- 主要风险和反方证据；
- 待用户确认的变更建议；
- 历史版本与变更原因。

投资逻辑变更门：

1. Codex 发现新证据与现有逻辑发生实质冲突。
2. Codex 生成“逻辑变更建议”，不直接覆盖当前逻辑。
3. 用户确认接受、拒绝或继续观察。
4. 确认后才更新当前逻辑，并保留变更前版本。

## 10. 定时任务模板

### 10.1 每日采集任务

职责：

- 检查新监管文件、新闻和公司行动；
- 采集最新财务、预期和指引相关数据；
- 保存原始快照并去重；
- 更新采集状态；
- 仅当发生实质变化时生成日报；
- 无变化时只记录任务成功。

### 10.2 每周研究任务

职责：

- 汇总当周增量信息；
- 更新管理层承诺状态；
- 标注市场预期和公司指引变化；
- 对比重要竞争对手；
- 检查投资逻辑的关键前提是否受损；
- 只写“发生了什么变化”，不重复生成公司基础介绍。

### 10.3 每月逻辑审计任务

职责：

- 检查原有判断哪些已被验证；
- 检查哪些判断已被证伪；
- 列出仍然属于推测的结论；
- 检查管理层承诺是否延期或改口径；
- 判断是否需要提出投资逻辑变更建议；
- 生成必须由用户回答的确认问题。

### 10.4 财报深度任务

不默认按固定时间空跑。

每日任务发现新财报后，写入待处理状态，再生成对应季度研究报告。

## 11. 定时任务运行规则

- 使用 Codex 桌面端项目级独立 Scheduled task；
- 定时任务直接在专用本地研究仓库中运行；
- 每次运行从固定、可版本化的提示词开始；
- 通过本地文件和 `state.json` 延续状态，不依赖聊天历史；
- 任务必须幂等，重复运行不应重复写入相同内容；
- 多个任务的时间需要错开，避免并发修改同一文件；
- 每次运行必须生成可检查的运行记录；
- 失败时停在可恢复状态，不在无确认时扩大权限；
- 任务提示词显式要求使用 `longbridge:longbridge` skill；
- MCP 工具和 CLI 命令只能使用 `config/longbridge-read-tools.yaml` 中的只读白名单，未列出的能力默认拒绝；
- Longbridge CLI 命令以当前安装版本的 `--help` 为准，不依赖过期命令示例；
- 每次采集保存统一 acquisition envelope，记录来源、传输方式、工具、参数、时间、状态、哈希和原始载荷路径；
- 先由确定性代码完成校验、去重和差异计算，再把新增或变化证据交给 LLM；
- LLM 默认不重复读取未变化的完整历史档案，避免成本浪费和无依据改写。

## 12. Longbridge 能力边界

### 12.1 采集原则

- 上市公司行情、财务、预期、监管文件、持股等结构化数据优先使用 Longbridge；
- MCP 用于交互查询、单对象试点和能力发现；CLI 用于验证后的批量任务、可复现命令和完整正文落盘；
- skill 只负责能力选择和研究流程指导，最终证据必须记录实际 MCP 工具或 CLI 命令；
- 机器可读采集统一使用 `--format json`；
- 复杂命令在固化前先执行 `longbridge <command> --help`；
- 保留完整原始输出，研究报告只引用对应路径；
- 只读查询可以在明确的网络失败规则下重试，或执行一次受控的只读传输切换；
- 传输切换必须保留原始失败记录，不得在 MCP、CLI 或其他来源之间静默替换；
- 任何金融写操作均不允许由本系统执行。

详细数据职责以 [数据来源与 LLM 分工规则](methodology/data-source-policy.md) 为准，允许调用范围以 [Longbridge 只读工具白名单](config/longbridge-read-tools.yaml) 为准。

### 12.2 当前验证基线

截至 2026-08-05：

- Longbridge MCP 已在当前 Codex 会话完成只读可调用验证；
- 本机 Longbridge CLI 已安装，版本为 `0.26.0`；
- CLI 授权与官方端点连通尚未完成验证，因此不能进入无人值守定时任务；
- MCP、CLI、plugin 和 skill 的安装、启用、授权、连通及可调用状态必须分别记录。

### 12.3 运行前必须分开验证的状态

- Longbridge plugin 是否已安装；
- plugin 是否已启用；
- plugin 是否已授权；
- plugin 是否实际可调用；
- Longbridge CLI 是否已安装；
- CLI 是否已授权；
- CLI 是否能连通官方端点；
- CLI 是否能成功返回目标市场的只读数据；
- Codex Scheduled task 是否具有目标目录写入和必要网络权限。

CLI、plugin/skill 和 MCP 的授权不得视为同一个状态。

## 13. 实施路径

### 阶段 1：单公司手动试点

- 选择 1 家公司；
- 创建目录和研究模板；
- 完成一次可复现的 Longbridge 只读采集；
- 生成首份公司基线档案；
- 人工检查事实、推测和情绪分类。

### 阶段 2：定时任务试运行

- 先启用每日采集和每周研究任务；
- 审查前几次定时运行结果；
- 调整去重、噪声和实质性变化阈值；
- 确认失败恢复和运行日志可用。

### 阶段 3：扩展到行业对比

- 扩展到同一行业的 3–5 家公司；
- 建立独立行业档案，使用 `company_id` 引用参与公司；
- 禁止在行业目录中复制完整公司档案；
- 建立可比的指标口径；
- 生成竞争对手变化和行业周报；
- 检查公司间的数据期间和会计口径差异。

### 阶段 4：稳定运行

- 增加每月逻辑审计；
- 建立异常任务提醒；
- 定期抽查原始证据与研究结论；
- 只在单公司模板稳定后继续扩大公司数量。

## 14. 当前已确认事项

- 本项目用于公司、行业和相关公众人物的长期研究与决策辅助；
- 不包装成保证赚钱的荐股工具；
- 计划使用 Codex Scheduled task、Longbridge plugin/skill 和 Longbridge CLI；
- 数据处理采用“来源采集—确定性处理—LLM 语义研究”三层职责，不能互相冒充；
- Longbridge MCP 用于交互与试点，CLI 在独立验证后用于批量和完整正文落盘；
- 定时任务显式使用 `longbridge:longbridge` skill，但证据必须记录实际 MCP 工具或 CLI 命令；
- Longbridge 能力采用默认拒绝、显式只读白名单；任何交易、订单、资金和 watchlist 写操作均禁止；
- 所有采集保存统一 acquisition envelope，不允许在来源或传输方式之间静默替换；
- 研究档案将维护在本地目录；
- 采用“公司主体—可交易证券—行业—公众人物”四类基础研究对象模型；
- 公司、证券、行业和公众人物共用底层研究协议，分别使用不同的上层模板；
- 公司可以拥有零个或多个可交易证券，未上市公司不强制创建证券对象；
- 同一公司的多个证券代码归属同一份公司档案；
- 行业通过 `company_id` 引用公司，不复制完整公司档案；
- 可独立引用、更新、审计或归档的最下层研究对象必须使用独立 ID 文件夹；
- ID 使用“3 位类型前缀 + 6 位独立递增序号”，并且分配后永久不变、不重用；
- 对象文件夹内的元数据和内容载荷使用同一 ID 命名；
- 编号规则以 `methodology/id-rules.md` 为唯一规则表；
- 公司与行业档案包含可交互的有向加权供应链影响图；
- 供应链关系作为全局唯一 `rel-*` 对象存储，公司和行业通过 ID 引用；
- 依赖权重由模型按统一评分表提出，必须保存证据、置信度、模型版本和人工状态；
- 供应链冲击模拟作为 `sim-*` 对象保存，结果是情景估算而不是股价预测；
- 公众人物使用 `per-*`，观点使用 `opn-*`，用户上传或主观提交使用 `sub-*`；
- 公众人物的关系是带时间范围的 `rel-*` 对象，不因当前职务而写成永久属性；
- 人物影响力、观点提取置信度和观点证据支持状态必须分开；
- 用户上传原文、用户批注和系统抽取结果必须分开保存；
- 公众人物的言论影响不得直接改写公司事实或供应链依赖权重；
- 用户提交和观点可以作为公司或行业建档入口，但原文只保存一次，通过 ID 关联多个研究对象；
- 未匹配的新公司、新证券或新行业只能形成待建档候选，用户确认后才由确定性程序分配正式 ID；
- 观点驱动归档可以触发只读核验和研究建议，不能直接修改事实、已确认关系权重或投资逻辑；
- 本文档属于模板，是后续讨论和修改的基线。
